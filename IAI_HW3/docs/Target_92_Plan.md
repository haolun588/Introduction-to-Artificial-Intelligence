# Kaggle 92% 改進計畫

制定／整理日期：2026/11/14。目標為課程 Kaggle 採計的 Macro-F1 **≥ 0.9200**；目前使用者回報最高 **0.9052**，差 **1.48 個百分點**。這是改進目標，不保證可達成。**已完成工作區整理與檔案核對；下列新訓練、跨精度推論檢查均尚未啟動。**

## 現況與保留版本

完整分數只維護於 [實驗總表](Experiment_Results.md)，來源為 [registry](../experiments/registry.json) 與各輪原始 summary。已盤點 7 個完整訓練、2 組集成，另有短跑及資料盤點。

保留 `weighted_sqrt` 為驗證基準，`weighted_lr3e5` 為目前成本較低的 Kaggle 最高分候選，另保存同分集成。已建立 [檔案雜湊與候選清單](../experiments/snapshot.json)，9 份 CSV 格式／ID 順序與 7 份 checkpoint metadata 均核對通過；尚未重新推論。`saved_models/checkpoint/` 仍是早期基準，交件時應從最終候選複製至獨立封裝目錄，不能誤當作最佳模型。

既有小範圍學習率搜尋已完成；URL、emoji、另一 seed 與兩組集成都未帶來已知最高分突破。停止擴大這些方向的盲目搜尋。neutral 為最弱類，但 benchmark 無標籤，不能假定 Kaggle 失分也全來自 neutral。1.48 個百分點 Macro-F1 不能直接換算成固定需修正幾筆。

## 方向評估與執行優先順序

目前瓶頸是提升能否在未見資料上重現，以及交件版本是否可靠。從目前兩個 seed 的差異與低互補集成結果，還沒有足夠證據支持擴大 seed 或集成搜尋。以下排序是依本機結果與實作成本的判斷，不是已證實的性能提升：

| 優先度 | 工作 | 理由與完成條件 |
|---|---|---|
| P0 | 對兩個保留候選執行 AMP／FP32 驗證比較 | 程式檢查確認驗證走 autocast、單模型 `predict` 未使用 autocast；先量化標籤／F1／機率／耗時差異，不能先把它當作低分原因 |
| P0 | 先做候選的獨立封裝與解壓推論演練 | 預設 checkpoint 仍是 baseline；需明確綁定模型、程式與 CSV，保留可交件版本 |
| P1 | 建立新控制組，再試較溫和類別權重及分層學習率 | 先做成本較低、單一變因的對照；每半輪評估與新方法使用同一比較流程 |
| P2 | 有希望的候選做額外切分確認 | 確認泛化方向，避免只迎合目前 900 筆驗證集 |
| P3 | 預算仍允許時試 FGSM | 實作、梯度／精度驗證成本較高，且沒有本作業的提升證據；最多兩個 epsilon |
| 暫停 | 更多 URL／emoji 規則、盲目 seed、集成權重搜尋 | 已做設定未提供突破證據；只有新證據出現才重新打開 |

PyTorch 的 [AMP 文件](https://docs.pytorch.org/docs/2.9/amp.html) 說明 autocast 會按運算選擇精度；這支持檢查兩條路徑，但不證明本模型的預測實際不同。當前判斷不涉及替換指定基底或新增外部訓練資料。

## 第一階段：確認評估可信，凍結比較方式（11/14–11/15）

**下一個具體工作是第 1 項跨精度檢查，約 30–60 分鐘的初步檢查，依發現調整。** 本次整理完成的是檔案／metadata／CSV 盤點，不將其算作模型推論一致性驗證。

1. 在既有 checkpoint 上對照驗證使用的 AMP 與正式推論使用的 FP32：比較標籤、Macro-F1、機率與 runtime。確認差異大小，若有差異則統一新實驗評估與推論路徑，先重建可比基準。已有重載檢查通過，但還不能代替跨精度檢查。
2. 檢查 optimizer／scheduler、梯度累積、加權 loss、checkpoint 選取與 ID／類別對齊；若找到問題，先隔離修正並重跑對照，不把 bug 修正與新方法混為一輪。
3. 固定每 0.5 epoch 評估與保存候選，最多仍 3 epochs；對原 2e-5 設定做一次新控制組，避免只在整數 epoch 評估而漏掉更佳模型。後續方法使用相同評估頻率。這本身增加選模機會，因此不能直接宣稱對舊流程公平提升。
4. 實驗總表、config／來源 hash／驗證／Kaggle／CSV hash 已建立。跨精度檢查仍需輸出各類 precision／recall／F1、錯判數、信心與機率；Emoji 分數未回報前保持未知。使用 `python tools/refresh_experiments.py --check` 確認總表未過期。

## 第二階段：至多四個新設定，改善泛化（11/15–11/19）

均使用原空白前處理、原 URL、seed 42、固定 8,100／900 切分、相同有效 batch 與新控制組評估頻率。每次只改一個主要因素，不組合失敗方法。

| 順序 | 具體實驗 | 要回答的問題 | 上限 |
|---|---|---|---|
| A | 將類別權重由 `n^-0.5` 改為較溫和的 `n^-0.25`，仍正規化為訓練樣本平均權重 1；其餘同控制組 | 現有加權強度是否限制 precision／recall 平衡？ | 1 個設定 |
| B | AdamW 分層學習率：最上 encoder 層 2e-5，每往下一層乘 0.9，分類 head 2e-5；其餘同控制組 | 降低底層更新幅度能否保留預訓練表示、改善泛化？ | 1 個設定 |
| C | 標準 embedding FGSM：`delta = epsilon * sign(grad)`，只擾動非 padding、非特殊 token；clean／adversarial loss 等權平均 | 以局部擾動訓練是否改善錯判與穩定性？ | 2 個 epsilon |

上述是待驗證假設，不預先承諾哪個會提高 Kaggle。FGSM 的兩個 epsilon 在正式跑分前，用訓練 batch 的 embedding 尺度與梯度檢查決定並寫入 config；不得用 benchmark 回饋選擇擾動幅度。先驗證擾動界限、mask、有限梯度、AMP／累積縮放、乾淨推論，以及不原地永久修改模型權重。每輪都從同一 BERT 基底重新訓練。

FGSM 概念依據：[Goodfellow 等，Explaining and Harnessing Adversarial Examples](https://arxiv.org/abs/1412.6572)。論文支持方法來源，不是本作業能改善分數的證據；此處採 embedding 上的適配，須實測。不要將 L2 正規化梯度的 FGM 實作誤標為 FGSM。

以新控制組為基準：Macro-F1 增益 **≥ 0.3 個百分點**為優先確認候選；0–0.3 視為待確認小增益，不稱為突破。這是資源分配門檻，不是統計顯著性。若 neutral 提升但整體下降，記錄權衡，不只報最好看的類別。四個設定均無穩定優勢就停止本輪搜尋，先檢討證據，不自動再加大量參數。

## 第三階段：確認候選，而非繼續迎合原驗證集（11/19–11/23）

第一階段就預先固定兩份額外的 90／10 分層文字群組切分，保存 seed、ID、hash；只讓第二階段最有希望的一個設定與新控制組各跑兩份，**共 4 次訓練**。兩者使用相同 seed、切分、評估頻率及計算預算。

檢查三份切分的配對分數差、平均差、三類 F1 與最差切分。候選至少在兩份切分改善且平均改善，才優先進入後續；若方向相反或微小，明確標為不穩定。切分可能互相重疊，且這是同一資料集，不是假裝取得全新獨立測試集，也不將結果當成顯著性證明。不得反覆更換切分直到候選勝出。

若第二階段無候選，這四次確認訓練暫不執行；先回顧錯判、規則與預算。不可只因原驗證已超過 92%，就認為 Kaggle 目標完成。

## 第四階段：有條件集成與最後資料利用（11/23–11/26）

- 只挑經確認的新候選與舊強模型，先在**相同未參與其訓練的樣本**比較互補；試一組預先指定的等權組合，最多三個模型。不平均各模型在自身訓練樣本上的分數，不把不同切分的 checkpoint 當成共用 holdout。
- 若集成沒有整體提升或誤判仍高度重疊，優先保留單模型；仍可按使用者偏好產生標示清楚的實驗提交檔。
- 2026/11/14 已核對講義第 14 頁：要求只在提供資料切出的訓練／驗證集合訓練及驗證，未明示免驗證的全資料重訓。**預設不執行全 9,000 筆重訓**；僅在課程規則另有明確允許時作額外候選。若允許，epoch／步數規則必須預先選定，不能拿已加入訓練的 900 筆再報驗證分數，並依全部訓練資料重算類別權重。既有最佳模型保留。
- 若不允許全資料重訓，直接使用符合規定的最佳驗證 checkpoint。始終不引入外部訓練資料、benchmark 標籤或換掉指定 BERT 基底。

## Kaggle 提交與決策

沿用使用者希望充分利用名額的偏好，正式實驗完成後均產生 1,000 筆合法 CSV，無論是否超過原驗證分數。每次記錄與目前最佳 CSV 的不同筆數；內容完全相同就不重複消耗提交名額。

按工作計畫記載的每 24 小時最多 3 次，實際剩餘額度以平台為準，不假設午夜重置。可提交三個**不同且有實驗意義**的候選：一個驗證優先候選、一個不同方法的探索候選、一個已確認設定的最終重訓／集成候選；沒有候選時不為填滿額度捏造變體。由使用者提交並回報，未授權工具代為提交。

Kaggle 作為外部結果紀錄，不逐筆猜 benchmark 標籤、不依 leaderboard 不斷微調權重或門檻。分數 ≥0.9200 時確認是課程採計欄位，保留對應 CSV、模型與設定，進入交件；不能將顯示分數當成尚未公布的最終榜保證。

## 預算、停止與交件（11/27–11/29）

核心上限：新控制組 1 次＋新設定 4 次＋額外切分確認 4 次＝**9 次完整訓練**；如規則允許，再加 1 次全資料重訓。是否執行後段由前段結果決定。依現有每輪約 17–23 分鐘，普通訓練估 20–30 分鐘、FGSM 粗估 30–50 分鐘，總計約 **4–6 GPU 小時**；這是估算，不含實作、除錯及機器降速，FGSM 需短跑後修正。

達 92% 即停止非必要探索。11/26 前仍未達標則保留最佳已知候選，停止無上限搜尋；11/27–11/29 優先完成乾淨解壓推論、依賴與 checkpoint 打包、CSV hash 對應、學號檔名及 E3／Kaggle 選定版本核對。依現有工作計畫截止為 11/30 23:59，最後交件前再核對平台公告。

完成標準分開記錄：研究目標達成（Kaggle 採計 ≥92%）、實驗流程正確、交件可重現。若分數未達標，誠實記錄，不能把「已跑完計畫」寫成「已達92%」。
