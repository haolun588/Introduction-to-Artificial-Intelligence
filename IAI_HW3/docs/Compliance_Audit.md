## 已辨識的缺口與處理順序

### 1. 最終交件產物未定案

`saved_models/checkpoint/` 仍對應 baseline。使用較早模型本身不違反指定基底規則，但若把它當成目前最佳候選封裝，會造成交件模型與宣稱的提交版本不一致。

下一步：依 [實驗總表](Experiment_Results.md) 明確選定模型與 CSV，設定 registry 的 `release_candidate`；建立獨立封裝目錄，包含必要程式、依賴、資料、選定 checkpoint、曲線及可執行 README，然後做乾淨解壓推論。實際提交檔名與平台狀態依 [交件清單](HW3_Work_Plan.md) 核對。

### 2. 基底模型的防錯與來源記錄：已修正

原問題是 `--base-model` 可指向任意本機目錄，而 run config 的名稱／revision 固定寫為指定 BERT。風險是誤用其他基底或損壞／混雜檔案後，紀錄仍看似合規；此前沒有發現既有實驗已使用禁用模型的證據。

2026/11/14 修正內容：

- [model_source.py](../src/model_source.py) 固定 5 個檔案的大小及 SHA-256；信任基準為直接查詢 [Hugging Face 官方 revision API](https://huggingface.co/api/models/google-bert/bert-base-uncased/revision/86b5e0934494bd15c9632b12f734a8a67f723594?blobs=true) 的結果。權重與其 LFS SHA-256 一致；其餘檔案先核對官方 Git blob ID，再固定其 SHA-256。
- [training.py](../src/training.py) 在初始化 GPU、載入模型及建立輸出目錄前完成離線驗證。只允許相同版本的完整副本，缺檔、大小／雜湊不符與額外載入設定一律拒絕；`.cache/` 可保留，但不作信任依據。
- `prepare` 下載後也驗證；新增 `main.py verify-base` 作為不啟動訓練的檢查入口。
- 新 run config 與選定 checkpoint 同時保存 `base_model_source` 與 `training_code_sha256`；使用實際驗證路徑載入，明確採 safetensors 並關閉 remote code。
- 舊 checkpoint 及 CSV 保持原樣，舊推論路徑不要求新欄位。修正只能防止後續誤用，不能補造歷史訓練來源鏈。

驗證：原有 13 項與新增 6 項來源檢查共 19 項測試通過；再新增並單獨通過 1 項 metadata 保存整合測試，合計 20 項。覆蓋同大小內容竄改、缺檔／截斷、額外 tokenizer／adapter／替代權重、偽造 cache metadata、失敗時不觸碰 GPU／載入器／輸出目錄，以及 run／checkpoint 來源欄位一致。整合測試僅用暫存的極小 CPU 線性模型，不是 BERT 實驗。真實本機基底亦通過 `main.py verify-base`；未重訓 BERT。

### 3. 預測與執行重現仍須完成

本次檔案核對沿用先前生成的 snapshot，證明目前檔案一致，無法替代從模型重現預測。最終候選應在乾淨封裝中重新推論，逐筆比較 CSV，保存執行命令、環境及 hash。

驗證目前採 CUDA AMP、單模型 `predict` 採 FP32，屬已知一致性待測項，**本身不是講義禁止事項，也尚不能認定是錯誤結果的原因**。不應把同樣的全套訓練重跑當成解決方式。

## 不應誤判的事項

- Kaggle 未達研究目標 92% 是成績／研究結果問題，不是違反作業規則；驗證集超過 92% 也不代表 Kaggle 達標。
- 驗證表現較差的模型仍有真實推論 CSV，不因此構成造假。
- Git 忽略本機模型與輸出不是違規，但交件 ZIP 必須實際包含所需 checkpoint 與資源。
- 全資料重訓、FGSM、分層學習率等仍屬計畫；沒有將尚未執行的工作當作已完成成果或既成違規。
